# Skim HTTP API

The local Go server exposes same-origin JSON under `/api`; all errors have `{ "error": "message" }`. Mutating requests require `Content-Type: application/json`. Responses never contain token or API-key values. Settings expose credential status and the actual private storage path; API-key updates are write-only deltas. The server persists review work per GitHub repository and pull-request number; loading another PR does not erase previous work. A changed head invalidates unpublished anchored work rather than silently publishing it on a different commit.

## State and resources

`GET /api/state` returns `State`:

```ts
type Side = 'LEFT' | 'RIGHT';
type RiskFactor = { text: string; side: Side; startLine: number; endLine: number };
type Risk = { level: 'low' | 'medium' | 'high'; probability: number; factors: RiskFactor[] | null; factorsError?: string };
type TestOnlyAssessment = { onlyTests: boolean; confidence: number; probability: number };
type PR = { provider: 'github'; owner: string; repo: string; number: number; title: string; body: string; url: string; author: string; baseSha: string; headSha: string; baseRef: string; headRef: string };
type File = { path: string; previousPath?: string; status: string; additions: number; deletions: number; patch: string; language?: string; patchStatus: 'available' | 'unavailable' | 'truncated'; risk?: Risk; testOnly?: TestOnlyAssessment };
type Group = { id: string; title: string; summary?: string; paths: string[] };
type LiveComment = { id: string; revision: number; path: string; startLine: number; endLine: number; side: Side; body: string; status: 'suggested' | 'pending' | 'published'; source: 'review' | 'verification' | 'manual'; threadId?: string; createdAt: string; headSha: string; stale?: boolean };
type DeletedComment = { id: string; revision: number; status: 'deleted' };
type Comment = LiveComment | DeletedComment;
type ChatThread = { id: string; revision: number; kind: 'global' | 'verification'; path?: string; startLine?: number; endLine?: number; side?: Side; messages: {role: 'user' | 'assistant'; content: string}[]; headSha: string; stale?: boolean; verification?: VerificationJob };
type VerificationJob = { id: string; revision: number; threadId: string; prKey: string; prUrl: string; baseSha: string; headSha: string; path: string; startLine: number; endLine: number; side: Side; question: string; status: 'queued' | 'preparing' | 'running' | 'summarizing' | 'cancelling' | 'complete' | 'failed' | 'cancelled'; startedAt: string; updatedAt: string; finishedAt?: string; error?: string; suggestionsError?: string; workspace?: Workspace; cleared?: boolean };

type Settings = { githubTokenEnv: string; githubTokenStatus?: 'saved' | 'environment' | 'missing'; providers: {id: string; name: string; kind?: 'openai' | 'typesafe'; baseUrl: string; apiKeyEnv: string; credentialStatus?: 'saved' | 'environment' | 'missing'}[]; roles: {chat: {provider: string; model: string}; review: {provider: string; model: string}; jev: {provider: string; model: string}}; acp: {command: string; args: string[]; managedRoot: string} };

type ReviewRun = {headSha: string; createdAt: string; report: string; rejected: {path:string;startLine:number;endLine:number;side:Side;body:string;reason:string}[]; error?: string};
type AnalysisTask = { status: 'running' | 'complete' | 'failed' | 'cancelled' | 'disabled'; completed: number; total: number; error?: string; skippedFiles?: {path:string;reason:string}[]; failedFiles?: {path:string;reason:string}[] };
type Analysis = { key: string; baseSha: string; headSha: string; generation: string; revision: number; risk: AnalysisTask; grouping: AnalysisTask };
type AnalysisUpdate = { analysis: Analysis | null; files: {path:string;risk?:Risk;testOnly?:TestOnlyAssessment}[]; groups: Group[] };
type Workspace = { id?: string; root: string; path?: string; count?: number; headSha?: string; status: 'not_created' | 'preparing' | 'ready' | 'in_use' | 'cleanup_pending' | 'cleanup_failed' | 'finished' | 'failed'; error?: string; finishedAt?: string; canDiscardChanges?: boolean };

type FileReview = { revision: number; reviewedPaths: string[] };
type FileReviewUpdate = { prKey: string; baseSha: string; headSha: string; fileReview: FileReview };
type State = { revision: number; pullRequest: PR | null; files: File[]; groups: Group[]; comments: Comment[]; chats: ChatThread[]; style: string; settings: Settings; reviewRun?: ReviewRun; fileReview?: FileReview; analysis?: Analysis; workspace: Workspace };
```

`patchStatus` is explicit: unavailable can include binary content or GitHub-omitted patches; truncated means patch counts do not cover the file's reported changes. Only `available` patches can be selected/anchored. `stale` work is retained for reference but cannot be approved/published/continued after a head/base change. `reviewRun` records the most recent completed review's exact scope; the UI must show skipped-file warnings and must not imply missing content was reviewed.

`risk` is an advisory change-impact category, not review order or a defect claim. Jev sees only this file's metadata and complete patch, excluding previous risk and PR-wide prose. Low covers narrative documentation/comments and localized limited-impact changes; medium covers bounded behavioral/integration changes; high requires a concrete serious consequence introduced by changed behavior or actionable instructions. Discussing security/concurrency/production is not itself a behavioral change. Operative configuration, policies, scripts, schemas, and destructive runbooks can be high even under a documentation path. Newness, size, or absent tests alone do not establish high risk. `reason` contains the selected rubric category and confidence, not a generated file-specific finding; confidence is not a defect probability or a level override. Missing/failed evidence stays unassessed.

`testOnly` classifies the file's **changeset**, not its filename or all existing code. The same Jev request asks separate typed `risk` and `test_scope` questions. Test scope chooses `tests_only` or `other_or_uncertain`; `confidence` is the answer confidence and `probability` is the returned probability of `tests_only`, not the probability of the selected alternative. Both answers must validate before the pair is saved. Embedded tests can qualify; mixed runtime changes, operational configuration, prose about tests, and uncertain evidence must not be assumed test-only. Prior `risk` and `testOnly` metadata are excluded from assessment/grouping evidence and reviewed-file identity.

The optional browser collapse preference requires an available complete patch, `onlyTests: true`, and finite confidence **and** probability in `[0.95, 1]`. Missing, failed, uncertain, or incomplete assessments remain expanded by default. No filename fallback exists. These model scores are advisory, not calibrated guarantees. Restored file URLs respect collapsing instead of forcing expansion. Explicit opening, file/line links, code selection, and composer focus still reveal code. Enabling the preference reapplies collapse to previously opened tests while protecting active selections and editors; classification never marks a file reviewed.

Cached per-file assessments include the selected Jev provider/model and a versioned policy fingerprint. A newer policy, or a formerly complete available file missing either assessment, recomputes the risk/test-scope pair; completed recommended units and user review state remain intact. Matching current-policy pairs are reused across reloads. Editing explanatory documentation does not bump that policy; changed PR evidence still invalidates analysis. The public three-level `Risk` shape is unchanged.

## Review inbox and commit metadata

`GET /api/inbox?username=LOGIN&repo=OWNER/REPO` returns the authenticated GitHub user's open review inbox by default. Both filters are optional: `username` changes the requested reviewer/assignee, not the authentication identity; `repo` narrows the search to one repository. Empty filters use the default. No diff is loaded, active PR changed, analysis started, or model called.

```ts
type InboxUser = { login: string; url: string };
type ReviewSummary = { prKey: string; provider: 'github'; owner: string; repo: string; number: number; title: string; url: string; author: string; updatedAt: string; draft: boolean; requested: boolean; assigned: boolean };
type ReviewInbox = { user: InboxUser; username: string; repo: string; reviews: ReviewSummary[]; complete: boolean; warnings: string[] };
type Commit = { sha: string; message: string; authorName: string; authorLogin: string; authoredAt: string; url: string };
type CommitList = { prKey: string; baseSha: string; headSha: string; commits: Commit[]; total: number; complete: boolean; warnings: string[] };
```

The inbox unions `is:open is:pr review-requested:LOGIN` with `is:open is:pr assignee:LOGIN`, deduplicating case-insensitive repository identity/PR number and retaining both source flags. Ordering is updated time descending, then canonical PR key. GitHub [documents that `review-requested` includes requests to teams the user belongs to](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests#search-by-pull-request-review-status-and-reviewer), unlike `user-review-requested`. Results reflect GitHub's visible/search-indexed pending requests, not historical completed reviews; assignment alone does not mean a review is outstanding.
Case folding is used only for deduplication; each row preserves the first validated GitHub response URL and its owner/repository casing in `prKey`, so opening an inbox row does not manufacture a differently cased local review identity.

The server follows safe sequential pages with 100 results/page. [GitHub search](https://docs.github.com/en/rest/search/search#about-search) caps each search at 1,000 results and may report incomplete results. `complete:false` and actionable `warnings` expose either case, including incomplete pagination; do not label such a response as all reviews. Narrow with `repo` and refresh, or use GitHub search. Searches are not an atomic snapshot and can change during pagination. Authentication, permission, and network failures return the standard HTTP 400 `{error:string}` rather than an empty/fake inbox; manual PR URL loading remains independent.
`complete` describes the returned search's pagination, not an independent audit of every GitHub repository. GitHub additionally limits global REST searches to up to 4,000 matching repositories, and inaccessible or not-yet-indexed PRs can be absent without an error. Use the repository filter when that scope matters.

`GET /api/commits?prKey=KEY&baseSha=SHA&headSha=SHA` lazily returns `CommitList` for the exact currently loaded PR. All identity fields are required, matching `PR.provider/owner/repo/number` and both loaded SHAs. The provider checks GitHub's base/head before and after pagination; a moving PR or local switch rejects the response with `{error:string}` instructing reload. This read never replaces state, comments, settings, or analysis. Cache only by all three identity fields and discard late responses after navigation.

Commit messages are full unmodified text; author names/dates come from Git commit metadata, and `authorLogin` is empty when GitHub cannot associate an account. URLs are constructed as canonical HTTPS `github.com/OWNER/REPO/commit/FULL_SHA`, never taken from untrusted response URL fields. Commits retain GitHub's PR-list order. The [PR commits endpoint](https://docs.github.com/en/rest/pulls/pulls#list-commits-on-a-pull-request) exposes at most 250 commits; `total` is the PR's reported commit count, and a capped/short result has `complete:false` with a visible warning to use GitHub. There is no per-commit inline-review diff: Diff, Guide, comments, and verification remain bound to the complete loaded PR comparison.

The Description view uses the existing full `State.pullRequest.body`; it requires no additional fetch.

Browser review URLs use `/github/OWNER/REPO/pull/NUMBER/{description|commits|diff|guide}`; Diff and Guide optionally include `?file=PATH`. The former Files route is no longer accepted. Opening or refreshing one calls `POST /api/pull-request` for current GitHub evidence before requesting discussions with the returned base/head. URLs intentionally do not pin old SHAs. Back/Forward restores the tab, and file selection replaces the current history entry. File links retain Guide when already in that tab; links from Description or other contexts enter Diff. Unit links enter Guide. Failed deep links keep their URL and show Retry/Go to inbox rather than silently showing an unrelated saved PR. Discussion errors offer **Reload pull request**, which reloads evidence before fetching comments again; it does not weaken snapshot validation.

## Review progress and published discussions

`GET /api/review/progress?prKey=KEY&baseSha=SHA&headSha=SHA` returns `{prKey,baseSha,headSha,run}` for the exact active snapshot. `run` is null when no matching process-local run exists. It does not acquire the foreground gate and stays responsive while the agent runs.

```ts
type ReviewProgress = {
  id: string;
  status: 'running' | 'complete' | 'failed' | 'cancelled';
  phase: 'preparing' | 'reviewing' | 'saving' | 'finished';
  findings: number; rejected: number;
  startedAt: string; updatedAt: string; finishedAt?: string; error?: string;
};
type PublishedComment = {id:string;author:string;body:string;createdAt:string;updatedAt:string;url:string};
type ReviewThread = {
  id:string; path:string; side:Side | ''; startLine?:number; endLine?:number;
  outdated:boolean; canReply:boolean; replyDisabledReason?:string; diffHunk?:string;
  comments:PublishedComment[];
};
type ReviewThreads = {prKey:string;baseSha:string;headSha:string;threads:ReviewThread[];warnings:string[]};
```

`preparing` covers the GitHub head check and checkout, `reviewing` the agent run, and `saving` comment validation and the final commit. `findings` counts new suggestions saved by the review and `rejected` the agent comments that failed diff validation. A failed/cancelled run commits no suggestions; only a successful commit reports `complete`. The agent's permission requests carry the run `id` as `jobId`. Run IDs distinguish repeated reviews, times are RFC3339, errors are credential-redacted, and a server restart discards transient progress (the persisted `reviewRun` remains). Do not infer completion from elapsed time or apply polls to another PR/snapshot.

`GET /api/review-comments?prKey=KEY&baseSha=SHA&headSha=SHA` returns `ReviewThreads` without changing local drafts or AI context. It fetches every GitHub review-comment page, checks remote base/head before and after, and groups roots/replies in creation/ID order. IDs are positive signed-64-bit decimal **strings**, never JavaScript numbers. Current anchors use GitHub's current `line`/`start_line`, not `original_line`; missing, cross-side, or file-level anchors are omitted. Missing roots are non-replyable and produce warnings. Clients must keep older or unavailable anchors off current code and still make these discussions accessible.

Public reads need no token; `canReply` permits an authenticated attempt, not a guarantee of repository write access. Fetches are bounded to 100 pages of 100 comments and 32 MiB aggregate body/path/diff text; unsafe links, page errors, and limits fail the request rather than returning a partial list. URLs are constructed from the known GitHub repository/PR/comment ID.

`GET /api/attachments?prKey=KEY&baseSha=SHA&headSha=SHA` returns `{prKey, baseSha, headSha, urls: Record<string, string>}`: GitHub's pre-signed image URLs for the PR description and every review-comment page, keyed by lowercase asset UUID. The server requests both with `Accept: application/vnd.github.html+json` and reads `<img src>` from `body_html`, keeping only `https://private-user-images.githubusercontent.com/...-UUID.ext?jwt=…` URLs (at most 1000). They work without a GitHub session, including for private repositories, but expire after about five minutes; clients fetch again when an attachment image fails. The PR's base/head must still match, otherwise the request fails with a reload hint. Nothing is persisted.

`POST /api/review-comments/replies {prKey,baseSha,headSha,threadId,body}` posts directly to an existing root thread and returns the resulting `PublishedComment`. It validates the exact active identity, root membership in that PR, remote refs, and a 1–60000-byte nonblank UTF-8 body without NUL (preserving composed whitespace). A missing token, stale identity, unknown root, or permission rejection is an error. A successful response needs no dependent read or local persistence.

Uncertain delivery returns HTTP 502 with `{error:string,code:'reply_delivery_uncertain'}`. It may already have posted: retain the composed text, refresh/check the thread on GitHub, and never automatically retry. A browser-level disconnect after submitting needs the same caution. Replies post independently of the Suggested/Pending review-comment queue and never finish or clean up the local workspace.

## Concurrency and revisions

Review/chat requests capture immutable evidence under a short gate and merge only their results. ACP verification instead admits a durable server-owned job and responds immediately: different threads can run concurrently in separate worktrees, while a duplicate active turn in one thread returns HTTP 409. PR navigation and independent review/chat/manual edits continue during checks. Background completion updates the captured saved PR, not the mutable active pointer; changed evidence retains the report in its stale thread and marks any resulting findings stale. Publication/local cleanup wait for active checks on their own PR, not checks belonging to other PRs. Existing review/chat/reply context conflicts remain. Client disconnect does not cancel accepted jobs; explicit cancellation and server shutdown cancel/drain their work.

`State.revision` is a durable, store-wide snapshot clock. Comment and chat-thread `revision` values are independent per-entity clocks, starting at 1 and increasing only on mutation; legacy entries begin at 0. A partial comment/thread response must not advance a client's full-state clock. Within the same PR snapshot, merge entity IDs and prefer higher revisions; preserve tombstones and locally newer partial results even when an older full response arrives. Reject responses from another PR/base/head or an obsolete client navigation epoch. Analysis and transient workspace status retain their separate scoped freshness rules.

`VerificationJob.revision` follows its thread's monotonic revision, including across successive job IDs. Merge global activity by `(prKey,threadId)`, preferring higher job revisions; timestamps are display metadata, not sufficient clocks for same-second follow-ups. Scoped verification polls merge thread/comment entity revisions without advancing `State.revision`. Startup marks interrupted jobs failed rather than replaying commands or paid requests. Detailed reports are retained even if subsequent finding extraction fails.

Human comments start `pending`; AI findings start `suggested`. Suggested UI actions are Approve/Edit/Deny; Approve changes status to `pending`, Edit preserves status, and Deny uses the deletion endpoint. Pending comments expose Edit/Delete. Deletion erases content and keeps a minimal `deleted` tombstone, hidden from lists and model evidence. Store startup migrates old manual `draft` and all `approved` comments to pending, other drafts to suggested, and `denied` comments to tombstones without losing credentials or publication journals. Active write APIs still reject the old status spellings.

`fileReview` is local human reading progress, not AI coverage or GitHub publication state. Its independent revision protects partial progress responses from older full-state responses; a newer empty `reviewedPaths` array must clear older marks. Missing legacy state means no reviewed files. Unit completion is derived from current member paths rather than persisted against model-generated unit IDs.

On PR reload, marks survive only if path, previous path, status, addition/deletion counts, patch, patch status, and language are unchanged; risk is excluded. Complete unchanged patches can retain progress when other commits advance the PR. Unavailable/truncated patches additionally require unchanged base/head, because their hidden content cannot be compared. Changed/renamed/removed files are cleared and the progress revision advances when the retained set changes. Regrouping and risk updates alone do not clear marks.

## Actions

- `POST /api/pull-request {url:string}` loads a canonical `https://github.com/OWNER/REPO/pull/NUMBER` URL, returns `State` immediately after real GitHub files and analysis status are persisted. Complete pagination and a final base/head consistency check must succeed before commitment. Independent server-owned grouping and (when Jev is configured) risk jobs start automatically; model calls never delay the load response. **Loading sends PR metadata with available file evidence to the review text-model provider, complete-file metadata/patches to the Jev provider when configured, and flagged files' patches to the review text-model provider for risk factors**, including private code when applicable.
- `POST /api/reviewed {prKey:string,baseSha:string,headSha:string,paths:string[],reviewed:boolean}` atomically marks/unmarks the listed files and returns `FileReviewUpdate`. The boolean must be explicitly supplied; paths must be nonempty, unique, and all present in the matching saved PR snapshot. Validation happens before any mutation. The lookup uses the saved PR key and preserves the active PR; stale refs or unknown paths reject the entire batch. Idempotent repeats do not commit or advance revision. This action calls no provider/model/Git operation and remains independent of comments, AI jobs, publication, and cleanup. Clients should keep controls pending until success, merge only matching scope/newer progress revision, and leave existing marks unchanged on error.
- `GET /api/analysis` returns `AnalysisUpdate`, a scoped polling resource containing **only** analysis status, per-path risks/test-only assessments, and groups with summaries. Match `analysis.key` to `PR.provider/owner/repo/number`, and match both SHAs and `generation` to the loaded state's analysis before applying a response; reject older `revision` values. Merge only risk/testOnly/groups/analysis, never replace comments, chats, style, settings, selections, or unsaved text. After an explicit refresh or settings change, obtain the new generation from the refresh response or a fresh state load; do not accept an arbitrary late response from an old generation.
- `POST /api/analysis {}` explicitly refreshes both jobs and returns `AnalysisUpdate` immediately with a new generation. It replaces the obsolete synchronous `/api/classify` action. Each complete-file Jev risk/test-scope pair is persisted independently and appears on the next poll. Failures do not discard other successful assessments or block grouping; unavailable/truncated evidence remains unassessed. Grouping `completed` becomes `total` only after the complete validated plan is committed.
- **Risk** is optional. Without a Jev role (`roles.jev` provider or model empty) the risk task is `disabled`: no per-file `risk`/`testOnly` values, no Jev calls, no errors; configuring Jev later starts it. When enabled, `risk.level` is derived from Jev's probability distribution under the `change-impact-flag80-factors-v3` policy: `high` when P(high) ≥ 0.8, `medium` when P(medium)+P(high) ≥ 0.8, otherwise `low`; `probability` is that supporting mass. Risk means potential impact if the change is wrong, not a defect finding.
  Once grouping settles (complete or failed), each `medium`/`high` file is explained by the review text-model role with the `risk_factors` schema `{factors:[{text:string,side:"LEFT"|"RIGHT",startLine:integer,endLine:integer}]}` (at most 3). Every anchor must fall on one side of one hunk of the file's patch; invalid anchors, markup, extra fields, or too many factors set `factorsError` for that file and keep its level. `factors: null` means not yet explained; `[]` means the model found no supporting evidence. Risk `total` counts all changed files plus flagged files; `completed` counts processed files (including skipped/failed) plus explained flagged files. An interrupted factor pass resumes on reload without repeating Jev calls.
- Recommended units use the configured **review text-model role**, not Jev, in one grouping request. Groups retain recommended reading order. Titles remain concise single-line labels (at most 100 Unicode characters); each group's `summary` is one or two plain-text sentences explaining its behavior and related files, never ranking reasons. There is no PR-wide introduction. Every changed path must appear exactly once, including incomplete files; invalid summaries, extra fields, unknown/omitted/repeated paths or invalid titles reject the entire response. Groups commit atomically under the grouping task and clear together on invalidation/retry. The `review-units-v3` policy refreshes older guides on PR load/settings changes without discarding current Jev risks or user work. Empty PRs get no groups without a model call. The prompt favors foundations/interfaces before consumers, keeps relevant implementation/tests/callers together, distinguishes stated intent from evidenced behavior, qualifies missing patches, and never claims tests passed. Missing configuration or excessive context produces a visible grouping failure, never invented groups; filesystem navigation remains usable.
  Jev retains its 96 KB per-file evidence bound. Grouping uses the text client's 4 MiB serialized-request guard, 8 MiB whole HTTP-response limit, and the provider's own context/output limits. Available evidence and generated descriptions are never silently truncated; provider responses that stop because of an output limit remain explicit failures.
  Grouping sends the concrete `review_groups` JSON schema for `{groups:[{title:string,summary:string,paths:string[]}]}`; risk factors send `risk_factors` (above). Suggested review sends `review_comments` for `{comments:[{path:string,startLine:integer,endLine:integer,side:"LEFT"|"RIGHT",body:string}]}`. All use OpenAI-compatible `response_format: {type:"json_schema",json_schema:{name,strict:true,schema}}`; every object declares all properties as required and `additionalProperties:false`. Schema names are fixed task identifiers, independent of provider display names/IDs. Endpoints must support this format. Errors surface without silent fallback or automatic retries; membership/completeness/anchor validation still applies. Chat and style import omit `response_format`.
- `POST /api/review {}` runs the configured ACP agent over the whole PR in a managed worktree at the inspected head (task `review`, base commit available) and appends its validated comments as `suggested` to the latest matching state. The agent ends its report with a fenced `json` block `{"comments":[{path,startLine,endLine,side,body}]}`; each comment must pass the same anchor, body and code-suggestion checks as manual comments, and failures are recorded in `reviewRun.rejected` with a reason rather than failing the review. `reviewRun.report` keeps the full report. A report without a readable block still saves `reviewRun` with `error`, then the request fails. Requires `acp.command`; the run is bounded to 30 minutes and cancelled if the request disconnects. Existing edits, chats, and verification results are preserved.
- `POST /api/style/import {owner?:string,repo?:string}` derives writing style from the authenticated user's existing GitHub review comments. Both owner/repo are required together; defaults to the loaded PR repository. Returns `{style:string,sampleCount:number}`. Requires the review model, and reports an error if no real samples exist. Pagination follows only sequential same-origin `Link: rel="next"` pages; GitHub's canonical `/repositories/ID/...` form of the named `/repos/OWNER/REPO/...` resource is accepted for the same suffix, but every request is rebuilt from the named repository and original query, never from the link.
- `POST /api/comments {prKey:string,baseSha:string,headSha:string,path:string,startLine:number,endLine:number,side:Side,body:string}` creates a human `pending` comment without AI or publication. It returns the live comment with ID, revision, timestamp, and current head. Identity is checked under the short commit gate. The body must contain 1–60000 bytes and be nonblank; its original whitespace is retained, including fenced-code indentation and final newlines. The range must be on one side of one complete hunk. Missing/truncated evidence and stale identities reject.
  Code suggestions use standard fenced `suggestion` Markdown inside `body`, not a provider-specific DTO. The UI prefills exact current RIGHT-side lines, preserves replacement indentation/newlines, supports empty deletion and safe longer fences for embedded backticks, and previews code without executing it. AI prompts permit precise evidence-supported replacements on RIGHT-side anchors only. Publication preserves the fenced body; approving a suggestion only makes the comment pending, never applies code or commits a branch.
- `PATCH /api/comments/ID {body?:string,status?:'pending'}` edits the body without changing status or approves a suggestion into pending. Body edits retain composed whitespace with the same size/nonblank validation. An unchanged pending status is idempotent; reset/deny status transitions are not supported (Deny uses DELETE). Stale suggestions cannot be approved. Published/deleted entries are immutable.
- `DELETE /api/comments/ID` returns `{id,revision,status:'deleted'}` and erases original content. Repeated deletion returns the same tombstone. Published comments and mutations during uncertain publication reject. Clients must merge the tombstone by revision before hiding it.
- `POST /api/publish {prKey:string,baseSha:string,headSha:string,event:'COMMENT'|'APPROVE'|'REQUEST_CHANGES',body?:string}` publishes pending comments in one review. Required identity is checked inside the gate before any provider call, including reconciliation. Stale pending comments block publication rather than being omitted. Suggestions/deleted entries are excluded. APPROVE may have no comments or summary; COMMENT needs pending comments or a summary; REQUEST_CHANGES needs a summary. GitHub head is checked before publication. Uncertain delivery is journaled and reconciled without resending. Success marks included comments published and cleans the managed checkout; cleanup failure preserves successful publication with HTTP 200 and `workspace.status:'cleanup_failed'`.
- `POST /api/review/finish {prKey:string,baseSha:string,headSha:string,discardChanges?:boolean,workspaceId?:string}` is the **Remove checkout** action, not the Finish Review publication dialog. It removes all owned default/thread worktrees for the selected PR without publishing and retains comments/conversations. Active review/checks for that PR return HTTP 409; unrelated PR checks and chat may continue. Dirty/unsafe worktrees remain with cleanup errors. Explicit discard requires `canDiscardChanges:true` and the exact confirmed workspace ID; for multiple checkouts that ID fingerprints the complete current set, so replacements/additions/removals invalidate old confirmation. Client paths never route deletion.
- `GET /api/workspace` returns `WorkspaceUpdate`. Match outer PR/base/head before merging only workspace. `count` is the number of owned checkouts (omitted when zero); multiple checkouts omit a misleading single `path`/`headSha`, with individual paths recorded in job metadata. A singleton retains its existing workspace ID; aggregate IDs fingerprint the current child IDs. The root/path are public filesystem locations, not credentials. Poll during preparation/use/cleanup; never replace comments/chats/settings from this resource. Completed jobs retain historical checkout details, while current aggregate status reports review cleanup. Shared bare caches and ownership markers remain after worktree removal.
- `POST /api/chat {message:string,threadId?:string}` creates/continues a global PR chat using the chat role; returns `ChatThread`. Omit threadId to create a new thread. An empty message or wrong-kind/stale thread is an error. Chat and PR loading do not create a worktree.
- `POST /api/verify {prKey:string,baseSha:string,headSha:string,path:string,startLine:number,endLine:number,side:Side,question:string,threadId?:string}` validates/adopts the exact displayed anchor, persists the user turn and job, and returns HTTP **202** `VerificationAccepted` before remote/Git/ACP work. Each thread uses its own exact-head worktree backed by the shared repository cache. Full ACP output is appended only to the thread. The configured Review model then extracts concise actionable findings using the existing `review_comments` schema; no concerns produces no comments. Extraction failure/missing configuration sets `suggestionsError` without discarding the completed report. The job never auto-publishes or applies a code suggestion.
- `GET /api/verifications?prKey=KEY&baseSha=SHA&headSha=SHA` returns `VerificationUpdate`: global latest-job metadata across saved reviews, plus the selected saved snapshot's verification threads and comments/tombstones. It does not depend on which PR is globally active. Without identity, the scoped fields/arrays are empty and only jobs are returned. Reject mismatching scope before merging entities; global activity remains usable on Home and after PR navigation.
- `POST /api/verifications/JOB_ID/cancel {prKey,baseSha,headSha}` cancels only that captured job and returns current job metadata. Cancellation stays `cancelling` while work winds down; terminal repeats are safe. Never infer permission ownership from an agent session ID: concurrent agent processes can return identical session IDs.
  Ignored build outputs do not prevent follow-up verification in an otherwise clean checkout, but cleanup conservatively retains them until explicit discard is confirmed. Preparation never executes repository hooks, filters, submodules, builds, or dependency installation. Git/ACP child process groups (Unix process groups; Windows kill-on-close Job Objects) are stopped and drained before the corresponding workspace lease is released.
- `POST /api/verifications/clear {}` marks every finished (`complete`, `failed`, `cancelled`) job `cleared:true`, advancing its thread revision, and returns `{jobs: VerificationJob[]}` with the changed jobs. Activity hides cleared jobs; their threads, reports and suggestions are unchanged. Active jobs are never cleared.
- `GET /api/settings` returns `Settings`; `PUT /api/settings SettingsUpdate` validates/persists settings and returns public `Settings`, never submitted key values. `providerKeys` is a write-only delta: an omitted/blank `apiKey` keeps the saved key, a nonblank value replaces it, and `remove:true` explicitly removes it. Remove and nonblank replacement together, duplicate updates, and unknown provider IDs are rejected. A saved key takes precedence over `apiKeyEnv`; removal falls back to that environment variable when available. `githubToken` follows the same rules for the GitHub token: a blank/omitted `token` keeps the saved one, a nonblank value replaces it, `remove:true` removes it, and a saved token takes precedence over `githubTokenEnv`. A present `style` (at most 32 KB) replaces the writing style in the same commit; omit it to keep the saved style. The read-only `credentialStatus` and `githubTokenStatus` report `saved`, `environment`, or `missing`. These public metadata fields are recomputed by the server, not trusted on writes.
  Providers are named instances, not built-in rows: fresh settings have `providers:[]` and all role provider/model pairs empty. Clients create instances by including a new stable unique `id` and required `name` in the providers array; multiple instances of the same kind/endpoint are supported. Names are trimmed, nonblank, and at most 100 Unicode characters. Rename only `name`, never `id`: roles and `providerKeys` remain ID-keyed, and names do not change credential binding, analysis generation, or cached results. Existing saved rows lacking a name normalize to their existing ID on load, preserving keys and roles. Removing every provider and clearing roles persists as empty across restarts. No model/base-URL environment variable seeds providers; optional `apiKeyEnv` references apply only to explicitly configured instances.
  Settings and private keys commit atomically in the same local JSON file, with `0600` file/`0700` directory permissions (on Windows, privacy comes from the per-user `%AppData%` ACL, not permission bits). Values are plain text on disk, not encrypted or keychain-backed; protect backups. Keys are destination-bound: changing a provider's protocol or base URL requires an explicit replacement/removal in that save, and deleting a provider deletes its saved key. Pre-rename failures leave old configuration/keys and running analysis untouched. Rename commits the whole pair; a subsequent directory-sync failure reports durability uncertainty (Windows has no directory sync; NTFS metadata journaling makes the rename the commit point). Internal credential revisions never appear in API responses or prompts.
  Changing an analysis model/provider/credential commits a new generation before cancelling stale work and starts only the affected analysis again; completed unrelated analysis and saved comments are retained. Reacquire the current generation after saving, merging only analysis fields so unsent review work survives. Provider `kind` defaults to `openai`; `typesafe` uses real Jev System One, not chat. Base URLs include the API prefix. Roles may be entirely empty while setting up; partially specified or incompatible roles are rejected. Anthropic and other gateways use the existing OpenAI-compatible endpoint, not a native adapter; the selected endpoint/model must accept the task-specific strict JSON schemas above. ACP uses `{command,args,managedRoot}` and keeps the agent's own authentication/model configuration. `managedRoot` is an absolute parent folder, not a checkout; empty resets to `<private data directory>/workspaces`. Legacy saved `workingDirectory` is ignored and never adopted/deleted; the new default is shown in Settings. Changing the root does not forget existing worktree ownership: prior roots remain tracked for safe cleanup.
- `GET /api/permissions` returns `{permissions: Permission[]}`; `Permission = {id,sessionId,title,details?,options:{optionId,name,kind}[],jobId?,threadId?,prKey?,prUrl?,path?,question?}`. Job/thread/PR fields are bound to the ACP turn, not guessed from the active review. Details contain bounded, credential-redacted supplied inputs/content/locations. Show them before approval. Activity and thread controls are nonmodal; polling continues independently of the current view. Explicit decisions only authorize that request, and ACP agents are not sandboxed by these controls.
- `POST /api/permissions/ID {optionId:string}` resolves one outstanding permission and returns `{ok:true}`. Unknown/expired permissions or invalid options are errors. Requests are never auto-approved.
- `GET /api/host` returns `{desktop:boolean}`: true when the Wails desktop app hosts the server. The web app uses it to route `target="_blank"` link clicks.
- `POST /api/open-external {url:string}` (desktop only; 404 otherwise) opens an absolute `http`/`https` URL without user info in the system browser and returns `{ok:true}`. Other schemes are rejected. Desktop web views do not open `target="_blank"` links themselves.
- `GET /desktop-launch?token=TOKEN` (desktop only) is the single cross-site navigation the server admits: the Wails start page (`wails://wails` or `http://wails.localhost`) navigates here with a per-launch 128-bit secret, and the response's same-origin meta refresh loads `/`. A wrong or missing token, deep links, and all other cross-site requests remain refused.

Background analysis belongs to the server, not the load/refresh HTTP request. PR switches, changed snapshots, analysis configuration changes and shutdown cancel obsolete work; generation and exact snapshot checks reject late results. Same-snapshot successful analysis persists per PR and is reused without paid reruns. Failed attempts remain visible until explicit refresh or relevant configuration change; interrupted work resumes on reload without repeating successful per-file decisions. Old stores without analysis metadata retain review work but recompute the obsolete classification when that PR is loaded. Poll while either task is `running`; terminal tasks may succeed independently. With no active PR, analysis is `null` and both resource arrays are empty.

Review/chat/style HTTP requests still respond when complete; verification HTTP requests respond on admission. Accepted verification jobs keep running after client disconnect or PR navigation, retain a five-minute bound, and expose durable status/errors. Shutdown cancels and drains workers before store closure; startup reports interrupted work rather than silently rerunning it. Process-group and ownership checks remain fail-closed if a checkout cannot be proven safe. Scoped commits preserve newer analysis, comments, and conversations; persistence failures are surfaced rather than silently discarding results.
