# Skim web UI

Svelte 5 + TypeScript + Vite, with [shadcn-svelte](https://www.shadcn-svelte.com/) (Nova) and [Tailwind CSS v4](https://tailwindcss.com/docs/installation/using-vite). All server communication and wire types are in `src/lib/api.ts`; contract is `../docs/api.md`.

## Development

```sh
# terminal 1: Go server (default 127.0.0.1:7437), trusting the Vite dev origin exactly
skim --dev-origin http://localhost:5173
# terminal 2
npm install
npm run dev        # http://localhost:5173, proxies /api to http://127.0.0.1:7437 (override: SKIM_API=...)
```

The dev origin must be exactly `http://localhost:5173` (fixed port, `strictPort`); open the UI at that URL, not `127.0.0.1:5173`.

## Checks and production build

```sh
npm run check      # svelte-check
npm run test:markdown # deterministic GFM, escaping, URL/image safety and file-navigation DOM tests
npm run build      # writes dist/, which the Go binaries embed at compile time (`skim --web-dir` serves another build)
```

Component interaction tests use `tests/mount-ui.ts` to supply App's shared tooltip context. The test loader compiles both local `.svelte.ts` and dependency `.svelte.js` rune modules.

## Visual conventions

- Shared shadcn primitives live in `src/lib/components/ui`; add components with `npx shadcn-svelte@latest add <component>` from `web/`. `components.json` records the registry and `$lib` aliases. `src/lib/utils.ts` provides class merging and component prop helpers.
- Tailwind v4 runs through `@tailwindcss/vite`. `src/app.css` defines the CSS-first theme and system light/dark colors, including diff-specific semantic tokens. Use Tailwind utilities on shared-component boundaries; retain scoped CSS for specialized diff/tree/resizer geometry. Native diff gutters and panel resizers keep their existing keyboard/pointer behavior.
- Use Lucide icons with concise visible labels for navigation and actions. `src/lib/components/IconButton.svelte` accepts `text` alongside its accessible `label` and tooltip; only familiar close, collapse, and scroll controls stay icon-only. Selected view/toggle controls use a high-contrast fill, and the active PR tab has an accent background and underline. Tooltips stay inside native dialogs when needed. `App.svelte` supplies the shared tooltip provider.
- Keep visible text for field labels, decisions, errors, publication scope and destructive actions. Remove routine instructions and duplicate descriptions; put setup guidance under disclosures. Actual PR descriptions, AI rationale and review content are not abbreviated.
- `ReviewLayout.svelte` owns panel sizing and visibility. Drag the file-tree or chat/review divider; arrow keys resize, Shift increases the step, Home/End use bounds, Enter collapses, and Escape cancels a drag. Collapse/restore buttons remain available beside the workspace; the diff takes freed space. Panels stay mounted, preserving input. Widths/visibility survive app navigation but reset on reload. Narrow screens retain the section switcher.
- Home uses a title-first inbox and a resume-review card. Settings has section navigation, provider tables with readable minimum column widths and keyboard-operable overflow controls, model-role cards, and a persistent save bar. Provider/agent settings and writing style still save separately.
- Description opens with an accent-bordered **review guide** card (unit count, unit titles in reading order, **Start guide**), followed by the author's description in its own neutral section. There is no AI overview. Diff and Guide keep a compact collapsible author description.
- Chat keeps its composer below the scrolling conversation. Verification outcomes link to Review comments rather than repeating the result. High/medium risk stays subtle; low risk has no visual badge. A flagged file opens with a tinted, left-bordered **factors worth checking** strip (level, confidence, level meaning, line-linked factors, and the reminder that unflagged files still need review); it can be collapsed per file. Diff comment controls appear on hover, keyboard focus, and touch.
- Diff code cells get basic GitHub-style syntax highlighting from Shiki (JavaScript regex engine, no WASM). The core and each language grammar are imported lazily and bundled as local chunks, so it works offline; colors come from the `--syntax-*` variables in `app.css` for light and dark. Each hunk's old and new sides are tokenized separately, so grammar state resets between hunks (full file contents are not fetched). Highlighting starts when a file nears the viewport, is cached per path and patch, and renders text-node spans only. Unknown languages, hunks with lines over 1000 characters, files over 5000 rows, and any tokenizer failure stay plain text.
- Preserve visible focus, native keyboard controls, explicit destructive confirmations, and reduced-motion preferences. Verify light and dark at both desktop and narrow widths; tables/code may scroll within their own regions, never widen the page.

## UI behaviour notes

- AI selection: click or drag line numbers (old gutter = LEFT, new gutter = RIGHT) to select code; keyboard Enter/Space and Shift-click are alternatives. Ranges stay within one file, side and hunk; missing-side rows and hunk gaps never add nonexistent lines. Only the number gutter suppresses native text selection, so code remains selectable/copyable. Files whose patch is `unavailable` or `truncated` cannot be selected.
- Selected gutter numbers share the continuous range shading without individual blue backgrounds/borders. `:focus-visible` remains for keyboard navigation in both unified and split layouts.
- Asking selected code dispatches a background ACP job. After acceptance, only the submitted question/selection is cleared; the current file/chat stays in place and another check can start immediately. Distinct threads run concurrently; only a follow-up in the same active thread is blocked. Ctrl/Cmd+Enter submits, with admission errors retaining the input. Completion never forces a tab/focus change.
- Inline **+** creates a Pending human comment. Suggested AI findings expose Approve/Edit/Deny; approval makes them Pending, while Deny deletes through the existing tombstone flow. Pending comments expose Edit/Delete. Insert/Edit code suggestion prefills the exact current RIGHT-side range and safely fences an editable replacement, including deletion and embedded backticks. Raw Markdown, replacement editing, and preview are alternate views of the same body; nothing is applied to source. Published comments remain read-only.
- Manual and AI drafts have independent store-backed anchors/text. Selecting/querying code never moves a manual draft; nonempty manual comments must be finished or explicitly cancelled before another + can move their anchor. Saving/cancelling either draft leaves the other intact. Polls and Home/Description/Commits/Settings navigation preserve both drafts. Changed PR/base/head makes each draft visibly unattached and blocks submission without discarding text. Ctrl/Cmd+Enter submits the focused composer; Escape cancels only that composer and returns focus to its gutter anchor. Empty input, busy actions and failures are handled in the relevant panel; saved comments appear below their end line and persist across reloads/PR switches.
- Comments from an earlier PR head (`stale`) are never drawn on current code; they appear under “Outdated comments”.
- Chat, verification messages, comments and PR descriptions share one Markdown renderer (`marked` GFM + DOMPurify). It supports paragraphs, headings, emphasis/strong/strikethrough, nested ordered/unordered lists, blockquotes, links, inline/fenced code, tables and disabled task checkboxes. Code keeps literal whitespace and language classes (no syntax highlighting); code blocks and tables scroll horizontally inside the message on narrow screens.
- All message text is untrusted: raw HTML is escaped before a strict tag/attribute sanitizer, and links allow only HTTP(S)/mailto or validated references to files in the current PR. HTML comments (`<!-- … -->`, such as PR template hints) are hidden, as on GitHub; comments inside inline or fenced code stay literal, and an unclosed `<!--` hides the rest of the text, as in HTML. **Images** render only in human-authored text, the PR description and GitHub discussions (`<Message images>`): Markdown images and raw `<img>` tags (GitHub attachments, including inside `<picture>`) load from absolute HTTPS URLs with `loading="lazy"` and `referrerpolicy="no-referrer"`, keep alt/title and numeric width/height, and open full size unless already inside a link (badges keep their link). Other sources (http, data, javascript) fall back to a link or text. The server CSP allows `img-src https:` for this. Chat, verification reports and local/AI comments never emit `img`, so a model-written URL cannot trigger a background request; their images stay explicit links with alt text. GitHub attachments (`github.com/user-attachments/assets/UUID`, legacy `user-images`) display GitHub's pre-signed URL from `GET /api/attachments` (`store.loadAttachments`, keyed by exact PR snapshot), so private-repository images load without a GitHub session; the link still opens the original URL. Signed URLs expire after about five minutes, so a failed attachment image refetches them (at most every 30 seconds) and re-renders. Until the first fetch returns, the unsigned URL is used, which private repositories reject. External links use `noopener noreferrer`. Known changed paths in prose, inline code or Markdown links open Diff, or retain Guide when already there; `path:12` and `path#L12` require positive safe line numbers, and click handling revalidates membership in the current PR. Arbitrary relative/local links and executable HTML are not supported. Commit messages remain plain text.
- Action-specific blockers replace a global busy flag. Background verification jobs do not occupy `busy.verify`; it is not a lifetime lock. New checks, review/chat, manual edits, and PR navigation remain available. Publication/cleanup waits for active checks on that PR only. Explicit cancel remains visible until the job winds down. Jobs and permissions poll independently of view; Activity shows progress/errors/decisions without a modal or an automatic focus change.
- Detailed ACP output belongs in a verification thread. Review-role extraction creates separate concise findings only when supported, optionally with code suggestions. An empty findings result adds no comments; extraction failure keeps the report and shows `suggestionsError`. Activity exposes the latest job per thread across saved PRs; scoped polls merge only matching thread/comment clocks. `VerificationJob.revision` orders same-second follow-ups and supersedes obsolete job IDs, preventing stale polls from resurrecting an old running check.
- Verify is a list-to-detail interface: only the check list or one conversation is displayed, with Back to checks preserving per-thread follow-up drafts. Explicit navigation resets the tool pane's scroll; background job updates never navigate. Technical IDs/workspace paths/times are folded into Details, and compact thread permissions omit repeated question text while keeping action inputs/options visible. The duplicate check-start message in the tool pane and the New check: select code button are removed; the global accepted-job acknowledgement remains.
- File navigation: every directory starts expanded for each new PR snapshot, including compact single-child chains. User collapses survive badge polls, filtering and view toggles; selecting another file opens its ancestors. Rows stay single-line with folder guides, icons and ellipsis names; full paths, status, risk level/confidence with its first factor, patch state and comment counts remain in tooltips/accessibility labels. Added/removed files have green/red document icons, modified files a muted ± icon, and renamed/copied files blue icons. High/medium risk uses subtle red/amber dots, low risk is quiet, and pending/unrated files use a dashed outline indicator (never when Jev is not configured). Files with comments show a small speech-bubble icon. There are no +/− line counts, folder counts or status/risk text badges in the tree. **Guide** retains the backend's exact unit/file order and selected file/lines, with titles and unit numbers rather than an alternate sort.
- Reader tabs: **Diff** uses the filesystem sidebar; **Guide** has a persistent unit rail with active-unit highlighting and reviewed counts. There is no separate reading-order toggle or store `navView`. `ReviewLayout` retains the last reader presentation while Description/Commits is visible. The rail has its own 220px default width, resize/collapse state, and mobile Units section. Larger 260–360px context sits beside continuous diffs when the remaining reader width is at least 780px, stacked otherwise. Explanations stick only while their files scroll and only when they fit the viewport. Navigator links reach explanation anchors; per-unit file links reach code without leaving Guide. Both sidebar components and flat path-keyed FileDiff slots remain mounted across tab changes.
- Scroll versus navigation: an IntersectionObserver tracks visible files and updates `selectedPath`/the file query without creating a navigation request or retargeting drafts. Explicit file, Markdown and comment links issue a monotonically numbered `fileNavigation` and reveal their target. Restored file URLs use `expand: false`: they scroll to the file header without overriding collapsed state. A short last file stays selected after a clamped end-of-scroll jump. New snapshots reset old requests. Reordering preserves the visible card's viewport offset. Gutter and line IDs include the complete path, so repeated line numbers across files cannot steal focus. Only the matching file owns a current inline composer; stale/missing-file drafts have one shared fallback, and there is one shared question panel.
- Unit links create a scoped `fileNavigation.unitId` intent with snapshot/generation guards, targeting the explanation rather than its first file. Passive scrolling never replays it, and stale analysis/snapshot changes clear it. A unit-only jump does not override a test's default collapse.
- **Collapse tests by default** is saved as the nonsecret browser preference `skim.collapseTests`, defaulting off. `isConfidentTestOnly` requires `patchStatus: 'available'`, `testOnly.onlyTests: true`, and finite confidence and test-only probability each in `[TEST_ONLY_THRESHOLD, 1]` (`TEST_ONLY_THRESHOLD = 0.95`). Jev judges the changed code; no filename heuristic remains. Unknown, uncertain, failed, and incomplete assessments stay open. Restoring a `?file=` location does not force expansion. Explicit file/line links, code selection, and composer focus still reveal code. An off→on preference transition reapplies collapse to previously opened tests, but retains visible selected code and active inline/comment/reply editors; already manually collapsed files stay collapsed. New snapshots reset per-file overrides. Classification never changes Reviewed marks. Preference persistence failures do not block review.
- Reviewed controls share `State.fileReview` across Diff, Guide, and the unit navigator. File checkboxes collapse on a saved reviewed transition and expand on unreview; ordinary collapse and the test default do not change marks. Unit checkboxes are derived all/mixed/none states and save the entire member list atomically. Completed units occupy one compact header row while retaining hidden FileDiff/editor instances. Unit or file navigation reopens content without unmarking. Keyboard focus returns to the unit checkbox when reviewing its last file hides the original control.
- Reviewed saves use path-scoped pending controls, not optimistic marks. Independent batches can overlap; overlapping paths wait. Errors remain visible and preserve saved state. `fileReview.revision` merges independently from the full State clock; late responses from a previous PR/epoch cannot replace current progress. The backend persists marks and invalidates only changed file evidence. Unit regrouping derives completion from file membership rather than carrying stale unit flags.
- Split alignment references canonical parsed rows, pairing deletions/additions by position within a contiguous changed block without crossing context or hunks. Excess lines have empty, noninteractive opposite cells. No-newline markers stay on their original side. Selection remains scoped to one file/side/hunk, and only that side highlights in split view. One keyed table preserves inline composer, comment-edit, and reply inputs while switching layouts; comments remain associated with their original side and appear once. Layout switches cancel active drags without discarding the range and preserve a visible line's position where scrolling permits.
- Automatic analysis: loading a PR returns immediately; the server runs text-model grouping, paired Jev risk/test-scope assessments per file when Jev is configured, and then factors for flagged files, all in the background. The UI polls `GET /api/analysis` only while a task is running, merges only analysis/risk/testOnly/groups (never replacing chat, settings, drafts or selection), and ignores responses whose PR, base/head SHA or generation does not match, or whose revision is older. Full-state and settings responses preserve newer per-file assessments together. The top bar shows Risk (hidden when the risk task is `disabled`) and Guide progress, and **Re-run analysis** (`POST /api/analysis`); failures show a clear message with Retry and never block review. Recommended order is shown only when the backend groups cover every changed file exactly once. Risk wording (level meaning, 80% flag threshold, scope reminder) lives in `src/lib/risk.ts`.
- Review context: Description, Diff, Guide, and review-unit descriptions use the available width. Opening a PR lands on Guide, the first tab. While grouping runs, Guide shows `GuideOverview` as a status panel with a **Read the diff meanwhile** shortcut; the file stream stays mounted but hidden, so open editors survive and files never reshuffle under the reader. If units fail, are unconfigured, or invalid, the panel explains why with Retry/Settings and the filesystem-order fallback appears below it. Unit summaries are one or two sentences. The author description starts expanded per snapshot and scrolls with the diff. Progress, errors, settings access, and retry reasons remain visible without disabling code review; generated prose is not verification evidence.
- Browser navigation: PR/view URLs use `/github/OWNER/REPO/pull/NUMBER/{description|commits|diff|guide}`, with the selected file in the query string for Diff and Guide. The former Files route is no longer accepted. Refresh fetches the PR again before requesting comments for its current snapshot. Back/Forward is serialized so a late response cannot navigate over a newer target; file changes replace history entries. Failed deep links retain their URL with explicit recovery. Both discussion error surfaces offer **Reload pull request**. The browser favicon uses Skim's three-line mark and adapts to light/dark browser themes.
- Review comments groups Pending, Suggested, and Published comments and shows the last completed review's coverage. Tombstones are never counted or rendered.
- Review progress polls its own scoped resource, independently of other running operations. A completion merges higher-revision entities into the latest local snapshot; it does not overwrite partial edits, reset unsent input, change the user's tab, or rewind workspace/analysis polls.
- Published GitHub threads remain a separate resource and appear inline or under GitHub. Older/unavailable anchors stay off current code. Reply inputs survive navigation and refresh; uncertain delivery still requires a successful refresh and explicit acknowledgement before another attempt.
- **Finish Review** opens a native dialog listing all Pending comments with Edit/Delete actions, a **Review outcome** selector (Approve / Comment only / Needs changes), and a summary. Suggestions are excluded until approved; stale pending comments are blockers. Approve can be bare, Comment only needs pending comments or a summary, and Needs changes requires a summary. **Submit review to GitHub** sends the dialog's exact PR/base/head, and an old overview cannot publish another PR.
- Settings remains a separate cog page. Its section links scroll locally without triggering PR routing; the active section tracks scrolling and stays visible in the horizontal mobile navigation. Activity and the cog retain their right-hand toolbar position. Review tools are Chat / Verify / Review / GitHub, with independent mounted editors. Changing tools resets only their outer scroll position.
- Both views stay mounted while navigating: the loaded PR, selected file/lines, active conversation, and unsent review inputs remain in place. Unsaved settings and writing-style edits survive returning to review and reopening Settings (but not a browser reload). Unchanged settings returned by a PR load do not replace local edits.
- ACP agent presets: Settings → Verification agent offers Claude Code (`claude-agent-acp` from `@agentclientprotocol/claude-agent-acp`), Pi (`pi-acp` from the community adapter https://github.com/svkozak/pi-acp; Pi's own `pi --mode rpc` is not ACP) and Custom. Selecting a preset only writes the existing command/args fields (the managed worktree folder stays separate); Custom keeps editable command and JSON args and restores your previous custom values if you switch back before saving. Skim never installs or logs in to an agent; the panel shows the install commands, sign-in notes and upstream links. A saved command equal to a preset with no args is shown as that preset, anything else as Custom.
- **AI providers** in Settings is a table of configured provider instances (Name, Type, Endpoint, Key status, Edit/Remove), empty on a fresh install with an empty-state message; there are no vendor preset cards. **Add provider** opens an inline editor: a required display name (1–100 characters; a label only, the opaque id identifies the instance), a type template (OpenAI, Anthropic OpenAI-compatible, TypeSafe · Jev, Custom endpoint) that prefills protocol/URL only inside the Add flow, an API key paste field, and a Connection settings section (protocol, required Base URL, optional environment variable) that is always open for Custom. You can add several instances of one type with different names/keys/URLs. New instances get a random opaque id (`crypto.randomUUID()`); renaming changes only the label, never the id, saved key or role bindings. Add/Edit/Remove only stage changes in the Settings draft (rows show “Not saved” / “Unsaved changes”); **Save settings** persists providers, keys, roles and ACP atomically. Cancel/Escape discards just the editor. The editor is not a nested form and Enter applies the editor, never saves settings. Keys are held in password inputs separate from serializable Settings, sent only as write-only `providerKeys` deltas, never echoed or kept in localStorage; blank keeps a saved key, **Remove saved key** stages removal. Changing a saved-key provider's URL/protocol requires a replacement or explicit removal (backend-enforced; the editor explains it). Removing a provider shows a warning and clears only roles bound to it; role pickers list providers by name and role model names are never overwritten when picking a provider. The Anthropic note describes OpenAI-compatibility mode only; genuine endpoint errors are shown as returned.
- Managed worktrees are prepared per verification thread, with distinct directories/leases/process journals and a shared bare repository cache. Activity/thread details retain the checkout used for each job; current aggregate status reports the number still owned. **Remove checkout** and successful publication clean every owned worktree for that PR. Dirty/unsafe worktrees remain with explicit errors; discard confirms the exact current checkout set. Hiding a panel, navigating, or disconnecting never cleans up or cancels accepted work.
- The UI follows the system light/dark theme. Settings uses a centered form width on desktop and a full-width scrollable page on narrow screens. Diff layouts, mobile views, review tools and primary actions pair icons with short visible labels; selected controls remain distinct in both themes. **Tests** retains the accessible name **Collapse tests by default**. Setup issues, role guidance and agent installation/authentication are folded into disclosures. Suggested, pending and published comments retain distinct status treatments.
